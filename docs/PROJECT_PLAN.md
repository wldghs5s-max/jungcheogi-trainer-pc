# 정처기 실기 PC 집중학습 플랫폼

## Project Plan & Product Direction

> 이 문서는 `jungcheogi-trainer-pc` 프로젝트의 제품 방향, 핵심 목표, 아키텍처 방향, 학습 철학 및 주요 기능 계획을 정의한다.
>
> 개발 과정에서 새로운 기능을 추가하거나 기존 기능의 방향을 변경할 때 이 문서를 기준으로 판단한다.
>
> 이 프로젝트는 기존 모바일 프로젝트 `jungcheogi-trainer`를 수정하는 프로젝트가 아니다.
> 기존 모바일 프로젝트는 **도메인 지식, 문제 구조, 채점 로직, 학습 로직을 참고하기 위한 선행 프로젝트**이며, 본 프로젝트는 별도의 PC용 애플리케이션으로 독립 개발한다.

# 1. 프로젝트 개요

## 1.1 프로젝트명

`jungcheogi-trainer-pc`

정보처리기사 실기 시험을 준비하기 위한 **PC 기반 집중 학습 플랫폼**이다.

기존 모바일 앱은 지하철, 이동 중 등 **5~10분 정도의 짧은 시간에 문제를 반복해서 보는 것**을 목적으로 설계되었다.

하지만 실제 시험 준비에서는 다음과 같은 학습이 필요하다.

- 긴 기출문제 풀이
- 복잡한 프로그래밍 코드 분석
- 개념의 체계적인 이해
- 암기 내용의 능동적 회상
- 교재/기출 문제 분석
- 틀린 이유에 대한 단계적 학습
- 일정 시간 동안 집중해서 공부하는 학습 세션

따라서 PC 버전은 기존 모바일 앱의 단순 확대판이 아니라 **집이나 회사, 공부방 등에서 앉아서 집중적으로 공부하기 위한 별도의 학습 환경**으로 개발한다.

# 3. 핵심 문제 정의

현재 정처기 실기 공부에서 다음과 같은 문제가 존재한다.

## 3.1 단순 암기의 한계

정처기 실기는 주관식 문제가 많기 때문에 암기해야 할 내용이 많다.

하지만 단순히 책의 내용을 읽고 그대로 외우는 방식이라면 별도의 학습 앱을 사용할 이유가 크지 않다.

따라서 앱은 단순한 암기 카드나 요약집이 아니라:

```text
이해
→ 압축
→ 회상
→ 검증
→ 반복
```

의 과정을 지원해야 한다.

---

## 3.2 교재를 읽고 AI에게 요약시키는 방식의 한계

기존 학습 방식에서는 기본서의 페이지를 촬영하여 AI에게 전달하고,

```text
책 읽기
→ AI 요약
→ 요약본 읽기
```

방식으로 학습할 수 있었다.

하지만 이 방식은 다음 문제가 있다.

- 실제 시험에서 기억을 꺼내는 훈련이 부족함
- 긴 교재 내용을 반복적으로 처리해야 함
- 학습자가 어떤 부분을 모르는지 명확하지 않음
- 교재 사진 OCR 오류 가능성
- 여러 페이지에 걸친 내용 처리의 불편함
- 빛 반사 및 촬영 상태에 따른 인식 오류

따라서 PC 앱에서는 **교재 내용을 단순히 요약하는 것보다 학습 가능한 구조로 변환하는 것**을 목표로 한다.

# 4. 학습 철학

## 4.1 AI가 대신 공부해주는 앱이 아니다

AI의 역할은 사용자를 대신하여 답을 제공하는 것이 아니라,

> 사용자가 스스로 이해하고 기억하고 문제를 해결할 수 있도록 돕는 것

이다.

따라서 AI 기능은 가능한 한 다음 순서를 따른다.

```text
힌트
→ 부분 설명
→ 단계별 설명
→ 전체 설명
```

사용자가 처음부터 모든 정답과 해설을 바로 보는 구조는 지양한다.

# 5. 암기/회상 시스템

정처기 실기의 암기 영역은 단순한 암기 카드보다 **능동적 회상(Active Recall)** 중심으로 설계한다.

## 5.1 기본 학습 흐름

```text
개념 학습
↓
핵심 내용 압축
↓
부분 회상
↓
힌트
↓
완전 회상
↓
정답 비교
↓
오답 분석
↓
간격 복습
```

---

## 5.2 동일 개념의 다양한 회상 난이도

하나의 개념을 여러 방식으로 출제할 수 있어야 한다.

예:

### Level 1 — 읽기

> TCP는 연결 지향형 프로토콜이다.

### Level 2 — 빈칸

> TCP는 **\_\_** 지향형 프로토콜이다.

### Level 3 — 부분 회상

> TCP의 주요 특징 중 하나는 연결 **\_\_** 방식이다.

### Level 4 — 완전 회상

> TCP의 특징을 작성하시오.

### Level 5 — 비교/응용

> TCP와 UDP의 차이를 설명하시오.

목적은 내용을 많이 보여주는 것이 아니라 **필요할 때 스스로 꺼낼 수 있도록 만드는 것**이다.

# 6. 학습 단위의 구조화

교재 또는 학습 자료를 단순 텍스트로 저장하는 것이 아니라 가능한 경우 다음과 같이 구조화한다.

```text
Concept
├── Definition
├── Keywords
├── Important Facts
├── Related Concepts
├── Common Confusions
├── Examples
├── Exam Patterns
└── Recall Questions
```

AI는 학습 자료를 이러한 구조로 변환하는 역할을 할 수 있다.

단, AI가 생성한 내용은 가능하면 원본 자료와 구분하여 저장한다.

# 9. 코드 읽기 도우미

PC 버전의 핵심 기능 중 하나.

복잡한 C, Java, Python 코드를 읽을 때 **코드의 각 줄을 직접 확인할 수 있는 인터랙티브 설명 기능**을 제공한다.

---

## 9.1 줄 단위 설명

사용자가 코드의 특정 줄을 클릭하면 해당 줄 아래에 설명이 펼쳐진다.

다시 클릭하면 숨겨진다.

기본 상태에서는 코드가 깨끗하게 보여야 한다.

---

## 9.2 코드 요소 분류

가능한 경우 코드의 요소를 다음과 같이 구분한다.

```text
[C 언어 키워드]
[표준 라이브러리 함수]
[사용자 정의 함수]
[사용자 정의 변수]
[자료형]
[연산자]
[헤더]
[클래스]
[메서드]
```

예:

```text
int calc(int *p)
```

에서:

```text
int
→ 자료형 / 언어 키워드

calc
→ 이 문제에서 정의한 사용자 함수

*
→ 포인터 관련 문법

p
→ 함수 매개변수
```

처럼 설명한다.

---

# 10. 코드 설명은 전체 문맥을 유지해야 한다

단순히 선택한 한 줄만 떼어 설명해서는 안 된다.

예를 들어:

```c
int result = calc(&value);
```

를 설명할 때는 `calc` 함수의 실제 정의까지 확인하여 설명해야 한다.

따라서 코드 설명 시스템은 가능하면:

```text
현재 줄
+
해당 함수 정의
+
변수 선언
+
호출 관계
+
실행 상태
```

를 함께 고려한다.


# 14. 내 설명 평가

문제를 풀고 정답을 확인하는 것에서 끝내지 않는다.

사용자가 직접 자신의 언어로 설명하도록 할 수 있다.

예:

> 이 코드가 왜 17을 출력하는지 설명하세요.

사용자의 답변을 AI가 평가한다.

단, 단순히 "맞음/틀림"만 제공하지 않고:

```text
✓ 정확하게 이해한 부분

△ 보완이 필요한 부분

? 아직 설명하지 않은 부분
```

으로 구분한다.

# 17. Ground Truth 원칙

이 프로젝트에서 중요한 원칙이다.

AI가 생성한 결과가 항상 사실이라는 전제를 두지 않는다.

특히 정처기 문제의 경우:

```text
실제 기출
교재
공식/신뢰 가능한 정답
실제 코드 실행 결과
```

등을 가능한 경우 **Ground Truth**로 사용한다.

AI는 그 자료를 바탕으로:

- 설명
- 요약
- 변형
- 힌트
- 학습 질문

을 생성하는 역할을 담당한다.

# 18. 프로그래밍 문제 검증

프로그래밍 문제는 가능한 경우 실제 실행 환경을 사용하여 검증한다.

특히:

```text
문제 코드
↓
실제 컴파일/실행
↓
실행 결과
↓
정답
```

을 Ground Truth로 삼는다.

AI가 추론한 실행 결과만을 정답으로 사용하지 않는다.

---

# 19. AI 생성 문제의 안정성

AI가 문제를 생성할 경우 다음 과정을 고려한다.

```text
AI 생성
↓
JSON Parsing
↓
Schema Validation
↓
문제 구조 검증
↓
정답 검증
↓
중복 검사
↓
필요한 경우 실제 실행 검증
↓
저장
```

생성 실패 또는 검증 실패한 문제는 사용자에게 정상 문제처럼 노출하지 않는다.

---

# 20. 오답 및 복습

오답을 단순히 "틀린 문제 목록"으로 관리하지 않는다.

가능한 경우 다음을 구분한다.

```text
문제를 몰라서 틀림
개념을 혼동해서 틀림
계산 실수
코드 추적 실패
문법 이해 부족
문제 해석 실패
암기 인출 실패
```

이를 기반으로 이후 복습을 구성한다.

---

# 21. 약점 프로파일

사용자가 단순히:

> C 언어를 못한다.

라고 판단하는 것이 아니라 더 구체적인 약점을 파악할 수 있도록 한다.

예:

```text
C

기본 문법        ✓
변수 추적        ✓
배열             ✓
포인터 선언      △
역참조            △
함수 인자 전달   ✕
이중 포인터      ✕
```

또는:

```text
Java

기본 문법        ✓
상속             △
오버라이딩       ✕
다형성           ✕
예외 처리        ✓
```

약점 분석은 충분한 학습 데이터가 축적된 이후 신뢰도를 높이는 방향으로 설계한다.

# 24. 데이터 저장 및 백엔드 아키텍처

이 프로젝트는 기존 모바일 앱과 달리 **PC를 백엔드 서버로 사용하는 구조**를 기본 방향으로 한다.

## Frontend

React + TypeScript 계열을 기본 후보로 한다.

GitHub Pages를 통해 정적 프론트를 배포한다.

---

## Backend

사용자의 개인 PC에서 실행한다.

기본 포트:

```text
8765
```

로 설정한다.

단, 8765가 이미 사용 중인 경우 변경 가능하도록 환경 변수로 관리한다.

예:

```text
PORT=8765
```

---

## 외부 접속

외부 PC에서 GitHub Pages에 접속하여 동일한 백엔드에 접근할 수 있도록 한다.

예상 구조:

```text
외부 PC
   ↓
GitHub Pages
   ↓
HTTPS API
   ↓
Cloudflare Tunnel
   ↓
개인 PC :8765
   ↓
Backend
   ↓
Database
```

Cloudflare Tunnel은 프로젝트 개발 초기에 반드시 연결할 필요는 없다.

먼저 로컬 환경에서:

```text
Frontend
↓
localhost:8765
↓
Backend
```

통신을 검증한다.

이후 외부 접근이 필요해지는 단계에서 Cloudflare Tunnel을 연결한다.

---

# 25. Cloudflare Tunnel

Cloudflare Tunnel을 사용하여 개인 PC의 백엔드를 외부에 연결할 수 있도록 한다.

단계:

```text
로컬 Backend 완성
↓
cloudflared 설치
↓
Quick Tunnel로 외부 테스트
↓
Cloudflare 계정/정식 Tunnel 구성
↓
HTTPS API 연결
```

Cloudflare 계정 및 도메인 관련 최초 설정은 개발자가 직접 진행하고, 이후 프로젝트 설정 및 실행 자동화는 가능한 범위에서 개발 도구가 지원한다.

---

# 26. 보안 원칙

백엔드가 인터넷을 통해 접근 가능해질 경우 최소한의 인증/보호 장치를 적용한다.

특히:

- Gemini API Key를 프론트엔드에 노출하지 않는다.
- API Key를 GitHub에 커밋하지 않는다.
- `.env`를 Git에 포함하지 않는다.
- 외부 API에는 인증을 적용한다.
- AI 생성 API를 무제한 공개하지 않는다.
- 민감한 설정은 환경 변수로 관리한다.

# 30. UX 기본 원칙

## 원칙 1 — 정보는 필요할 때 보여준다

코드 설명 등은 기본적으로 숨겨두고 사용자가 클릭했을 때 보여준다.

## 원칙 2 — 전체 문맥을 유지한다

코드의 일부를 설명하더라도 전체 코드와의 관계를 잃지 않도록 한다.

## 원칙 3 — AI 설명은 단계적으로

가능하면:

```text
힌트
→ 부분 설명
→ 단계별 설명
→ 전체 설명
```

순서를 지원한다.

## 원칙 4 — 사용자가 직접 생각하는 시간을 보장한다

정답을 너무 빠르게 노출하지 않는다.

## 원칙 5 — 원본과 AI 생성 내용을 구분한다

교재/기출 원문과 AI의 해석/생성을 명확히 구분한다.

## 원칙 6 — 모바일 UI를 그대로 확대하지 않는다

PC의 넓은 화면을 적극적으로 활용한다.

# 31. PC 화면의 기본 방향

PC에서는 여러 정보를 동시에 확인할 수 있는 구조를 적극적으로 활용한다.

예:

```text
┌────────────────────────────────────────────────────┐
│ 문제 / 학습 세션                                   │
├───────────────────────────┬────────────────────────┤
│                           │                        │
│       문제 / 코드         │      학습 정보         │
│                           │                        │
│                           │  변수 상태             │
│                           │  개념                  │
│                           │  힌트                  │
│                           │  오답 분석             │

└───────────────────────────┴────────────────────────┘
```

단, 화면을 복잡하게 만드는 것이 목적이 아니다.

사용자의 현재 학습 목적에 필요한 정보만 노출한다.

# 33. 개발 에이전트에 대한 중요 지침

AI 개발 도구는 다음 원칙을 따른다.

### 기존 프로젝트를 함부로 수정하지 않는다.

PC 프로젝트는 별도 레포지토리다.

### 구현 전에 관련 문서를 확인한다.

최소한:

```text
PROJECT_PLAN.md
EXISTING_APP_ANALYSIS.md
```

를 확인한다.

### 기존 모바일 앱의 동작을 추측하지 않는다.

필요한 경우 원본 프로젝트를 참고한다.

### 기능을 추가할 때 기존 데이터 모델과 충돌하지 않는지 확인한다.

### AI 기능을 추가할 때 Ground Truth를 고려한다.

### AI가 생성한 결과를 무조건 사실로 취급하지 않는다.

### 실제 실행 가능한 코드는 가능한 경우 실제 실행 결과를 기준으로 검증한다.

### 큰 변경은 단계별로 구현한다.

각 단계마다:

```text
구현
→ 테스트
→ 검증
→ 문제 수정
→ 다음 단계
```

를 따른다.
